# Gateway Module

Entry point for all LLM requests. Orchestrates auth → rate-limit → cache → routing → streaming.

## Responsibility boundary

`GatewayController` is HTTP only — no business logic. `GatewayService` is business logic only —
no Prisma, no res.write(). `StreamService` owns the SSE lifecycle.

## Request pipeline

```
POST /v1/chat/completions
  → RequestIdMiddleware   (stamps X-Request-Id on every response, before guards)
  → AuthGuard             (validates tenant API key, populates req.tenant)
  → RateLimitGuard        (RPM → budget → TPM; see ADR-003)
  → CacheInterceptor      (exact-match lookup; see ADR-004)
  → GatewayController
  → GatewayService.complete() or completeStream()
  → AdapterRegistry → IProviderAdapter  (see ADR-001)
  → StreamService.proxy() → res.end() → enqueueUsageJob() (see ADR-002)
```

## Guard rules

**Never change the guard order.** `AuthGuard` must run before `RateLimitGuard` because the
rate limiter needs `req.tenant.tenantId`. `RequestIdMiddleware` must run before everything
to stamp 401s and 500s with a request ID.

See [ADR-005](../../../docs/decisions/ADR-005-adminguard-authguard-separation.md) for the
`AuthGuard` vs `AdminGuard` split. This module uses only `AuthGuard` — never `AdminGuard`.

## Streaming (@Res without passthrough)

`GatewayController` uses `@Res()` (passthrough: false). NestJS does not serialize the return
value — the controller owns the full response lifecycle. Both paths call `res.status(200)`
explicitly because NestJS defaults to 201 for POST when passthrough is disabled.

Mid-stream errors are signalled as an SSE `{ error: true }` event followed by `[DONE]` —
the HTTP status code cannot be changed after headers are flushed.

## x-user-id / userLabel — PII rule

`@Headers('x-user-id')` is forwarded as `userLabel` in `UsageJobData`. It **must** be an
opaque token (hashed user ID, session UUID). Never store emails, names, or real identifiers.
Callers are responsible for pseudonymization before sending this header.

## Key files

| File | Purpose |
|------|---------|
| `gateway.controller.ts` | HTTP layer, `@Res()`, sets rate-limit headers |
| `gateway.service.ts` | Routing, adapter calls, job enqueue |
| `dto/chat-completion-request.dto.ts` | Input validation: ≤100 messages, ≤1M chars each |
| `dto/gateway-request.dto.ts` | Internal request shape passed to adapters |

## Invariants

- `res.status(200)` called before any write on both streaming and non-streaming paths
- `cacheKey` passed through `complete()`/`completeStream()` to the usage job
- `requestId` generated by middleware; never self-generated inside service
